2.  **[프론트엔드 데이터 매핑]**: API 응답 시, 권한 미달로 인해 `Growth` KPI 값이 아예 누락되는 경우가 있습니다. 프론트엔드는 이 경우를 대비해 **Placeholder 값 (N/A 또는 0)**을 받아들이고 UI가 깨지지 않도록 처리하는 로직이 필요합니다.

## Ⅱ. 핵심 애니메이션 컴포넌트 스펙 (Key Components Specification)

다음은 영상의 흐름에 따라 사용될 주요 시각 요소와 그 동작 원리(Animation Principle)를 정의합니다. **애니메이터는 이 '원리'를 최우선으로 이해해야 합니다.**

### 1. 진단 결과 변화 애니메이션: The Progress Arc (진행률 그래프)
*   **목표:** 학생의 현재 상태가 어떻게 개선될 수 있는지 시각적으로 드라마틱하게 보여준다.
*   **기술적 제약/규칙:** 이 그래프는 **시간(Time)**에 비례하여 부드럽게 상승하며, 데이터 증가 속도는 API Mockup에서 정의된 `[Progress_Rate]` 값을 반영해야 합니다. 급격한 변화는 애니메이션으로 완화되어야 합니다 (J-Curve Easing).
*   **시각적 연출:**
    *   **Start:** Pain 영역(Dark Blue/Red Tone)을 배경으로, 그래프가 낮은 지점에서 시작한다.
    *   **Transition Point:** '솔루션 적용'이라는 타이틀과 함께 Accent Yellow로의 색상 전환이 발생하며, 애니메이션이 가속화된다 (The Turning Point).
    *   **End:** 최종 Gain 영역(Accent Yellow/Dark Blue)에 도달하며 최고점에 머문다.

### 2. 데이터 시각화: Skill Gap Meter (스킬 간극 측정기)
*   **목표:** 현재의 약점과 이상적인 목표치 사이의 '간격'을 직관적으로 보여준다.
*   **기술적 제약/규칙:** 각 스킬 항목(예: 화성학 지식, 리듬 정확도)마다 *개별 진단 결과 데이터*가 존재합니다. 이 데이터를 기반으로 게이지 바가 채워지거나 비어나는 애니메이션을 사용하며, **데이터 값이 0에 가까울수록 더 긴 시간 동안 시청자의 주의를 끌어야 합니다.**
*   **시각적 연출:**
    *   게이지 바는 **반투명한 Dark Blue 배경** 위에 그려지고, 실제 측정된 점수는 Accent Yellow로 채워집니다.
    *   Gap이 클수록 (빨간색 경고 표시가 나타날 여지가 많을수록) 애니메이션의 무게감(Weight)과 톤 다운된 긴장감을 유지해야 합니다.

### 3. 정보 제시 방식: 데이터 계층화 (Layered Information Reveal)
*   **목표:** 한 번에 모든 정보를 주지 않고, 시청자의 흥미가 최고조일 때 핵심 데이터를 노출한다.
*   **기술적 제약/규칙:** Writer의 스크립트 흐름(Flow)을 따라, **최대 3가지 정보 모듈만 동시에 화면에 존재할 수 있습니다.** (정보 과부하 방지).
*   **시각적 연출:**
    1.  Pain 제시: 큰 헤드라인 (Montserrat Bold)과 함께 핵심 데이터가 먼저 등장한다.
    2.  원인 분석: 데이터를 뒷받침하는 차트(Skill Gap Meter 등)가 부드럽게 *팝업되어* 나타난다.
    3.  솔루션/Gain: 가장 밝은 Accent Yellow와 간결한 CTA 메시지가 화면을 가득 채우며 마무리된다 (Focus & Impact).

### 2. 기술 제약 사항이 서사에 미치는 영향 분석

기술적 제약사항은 단순한 구현 문제가 아니라, **감성적 몰입을 위한 '구조'**로 작용합니다.

#### A. 시각적 일관성 (Designer 영역의 반영)
*   **제약:** Key Visuals 제작 지시서에 명시된 브랜드 컬러(`Dark Blue`, `Accent Yellow`)와 타이포그래피 규칙은 감정의 색채를 직접적으로 제어합니다.
*   **분석:** 'Pain' 구간에서는 **경고색(Yellow)**을 사용하여 즉각적인 불안감을 유발하고, 'Gain' 구간에서는 **신뢰색(Blue)**으로 전환하여 시스템에 대한 신뢰를 구축해야 합니다. 이 색상 변화의 속도와 강도가 시청자의 심박수와 동기화되어야 하며, 이는 코다리팀이 정의한 API 데이터 흐름과 정확히 매핑되어야 합니다.

#### B. 청각적 흐름 (Sound Design 영역의 반영)
*   **제약:** 기술적 요구사항(API 응답 스키마 및 지연 시간)은 영상 편집 시 사운드 디자인의 타이밍을 결정합니다.
*   **분석:** 데이터가 제시되는 순간, 혹은 AI 분석 결과가 화면에 나타나는 **'전환점(Transition Point)'**에서 사운드의 톤과 볼륨이 급격하게 변화해야 합니다. 기술적 지연이나 오류 발생 시 (예: LLM 호출 실패의 미세한 흔들림) 이를 **불안정함**으로 청각화하여, 사용자가 느끼는 불안감이 곧 시스템의 불안정성으로 연결되도록 설계해야 합니다.

### 3. 최종 권고 사항 (Actionable Insight)

1.  **데이터 시각화 최우선:** 기술적 제약(API 구조)을 복잡하게 설명하는 대신, **'Gap Score' 변화 그래프**를 영상의 중심 축에 배치하여 감정적 흐름을 지배하도록 하십시오. 추상적인 수치보다 시각적 변곡점이 곧 서사가 되게 해야 합니다.

3.  **후크 강화:** 도입부 후크는 '노력 부족'에 대한 비난이 아니라, **'당신의 잠재력이 측정되지 않고 갇혀있다'**는 구조적 문제 제기로 시작하여 기술적 해결책(AI)로 자연스럽게 유도하는 것이 가장 강력한 전환 경로입니다.

### 2. 시청 지속 시간 극대화 전략 (Retention Strategy)

## 3. 기술적 병목 구간 (Technical Bottleneck Analysis) 및 해소 방안

이 시스템의 가장 큰 병목은 **'데이터 제시 시점의 권한 검증 실패'** 와 **'서사(Narrative)와 데이터 변화율 동기화 실패'** 입니다.

### 🔴 Bottleneck #1: 실시간 RBAC 기반 데이터 필터링 (가장 중요)
*   **문제:** 사용자의 구독 레벨이나 진단 요청 권한에 따라 특정 KPI (`Monetization` 등 민감 정보)의 존재 여부 자체가 달라져야 합니다. 단순히 API 호출 시 403 Forbidden을 반환하는 것만으로는 부족합니다. 프론트엔드에서 '데이터 없음'이 아닌, '권한으로 인해 볼 수 없음'이라는 **서사적 해석**이 필요합니다.
*   **해소 방안:** 백엔드 레이어(Controller/Service)에서 `Role-Based Access Control (RBAC)`를 최우선으로 수행해야 합니다. 만약 특정 KPI 데이터가 조회 시도된 권한을 초과한다면, 해당 필드는 **`null`로 반환하되**, `kpiMetrics` 배열 내부에 `<isRestricted: true>` 플래그를 추가하여 프론트엔드에 '데이터 제한' 로직을 전달해야 합니다.
*   **DB/Logic Impact:** `Diagnosis_Results` 조회 시, 요청하는 `Role`과 `diagnosis_type`의 조합으로 가용 데이터를 필터링하고, 그 결과를 JSON 스키마에 맞춰야 합니다.

### 🟡 Bottleneck #2: 감성 서사(Narrative)와 데이터 변화 추이 동기화
*   **문제:** 'Hook 2'는 "어떤 노력 때문에 어떤 결과가 나왔다"는 **인과관계**를 시각적으로 보여줘야 합니다. 즉, 단순히 `initialValue`와 `finalValue`의 차이만으로는 부족하고, 이 변화율을 감성적 메시지(`narrativeMessage`)에 녹여내야 합니다.
*   **해소 방안:** API 서비스 로직 내에 **'Storytelling Service Layer'**를 추가해야 합니다. 이 레이어는 데이터 비교 (Initial vs Final) $\rightarrow$ 변화량 계산 $\rightarrow$ 사전에 정의된 템플릿(예: "XX 지표가 +15% 개선되면서, 당신의 진정성이 증명됩니다.")에 따라 `narrativeMessage`를 동적으로 생성하는 역할을 맡아야 합니다.
*   **기술적 구현:** 이 서비스는 단순한 계산이 아니라, KPI 변화율을 기준으로 텍스트 템플릿을 선택하는 **Rule Engine** 구조로 설계되어야 안정적입니다.

### 🟢 Bottleneck #3: 데이터 트랜잭션 및 일관성 확보
*   **문제:** 진단 과정은 여러 단계의 API 호출(진단 $\rightarrow$ 저장 $\rightarrow$ 리포트)으로 이루어지므로, 중간에 네트워크 오류나 서버 크래시가 발생하면 데이터 불일치가 생길 수 있습니다.
*   **해소 방안:** 모든 주요 API 로직(`GET /api/v1/hook2_analysis`)은 반드시 **DB 트랜잭션(Transaction)**으로 묶여야 합니다. 만약 리포트 생성 중 KPI 저장에 실패하면, 진단 결과까지의 모든 작업이 롤백되도록 보장해야 합니다.
