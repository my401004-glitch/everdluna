## 🛠️ Funnel Flow 핵심 실패 케이스 분석 및 기술 사양서 (Designer용)

**문서 목적:** 유료 전환 퍼널(Paid Conversion Funnel)의 각 게이트 지점에서 발생 가능한 치명적 오류를 정의하고, 이 오류가 사용자에게 전달되는 방식과 시스템이 기록해야 할 트랜잭션 데이터를 표준화합니다.
**대상 에이전트:** Designer (UX/UI & Visual Storytelling 담당)
**개발 원칙:** 모든 실패 상태(Error State)는 단순한 '오류'가 아닌, **사용자의 학습 기회이자 다음 단계로의 동기 부여(Pain $\to$ Gain)**여야 합니다.

### 🔴 Failure Case 1: 권한/접근 제한 실패 (Authorization Gate)
*   **발생 위치:** 유료 콘텐츠(Premium Diagnosis Report, 특정 기능) 접근 시도.
*   **비즈니스 문제:** 사용자가 구독 만료 상태이거나, 현재 등급으로 해당 리포트 접근이 불가능함.
*   **기술적 원인 (Backend):** Role-Based Access Control (RBAC) 검증 실패. `User` 테이블의 권한 레벨(`user_role`) 또는 `Subscription_Status`가 요구 조건 미충족.
    *   **에러 코드:** HTTP 403 Forbidden / 커스텀 API 코드: `AUTH_FORBIDDEN`
    *   **트랜잭션 기록 필요 항목:** `Diagnosis_Log` 테이블에 '권한 부족' 발생 로그(`reason=AUTH_FORBIDDEN`)를 필수 기록.

| UI/UX (Designer) 가이드라인 | 메시징 전략 (Copywriting) | 비고 (Kodari의 검증점) |
| :--- | :--- | :--- |
| **톤앤매너:** 절망적이지 않고, "다음 단계로 나아갈 수 있는 방법"을 제시. | **핵심 내용:** "이 기능을 사용하려면 [유료 서비스]가 필요합니다." + **해결책 명시:** '구독하기' 버튼이나 요약된 가치 제안(Value Proposition) 배치. | 단순히 403 에러 메시지를 보여주면 안 됩니다. *왜* 접근할 수 없는지, 그리고 *어떻게* 풀어나갈 수 있는지의 흐름이 중요합니다. |

### 🟡 Failure Case 2: 결제 및 인증 실패 (Payment Gateway Error)
*   **발생 위치:** 최종 구독/결제 단계(Paywall).
*   **비즈니스 문제:** 카드 오류, 네트워크 불안정, PG 시스템 시간 초과 등으로 거래가 완료되지 않음.
*   **기술적 원인 (Backend):** 외부 결제 게이트웨이(PG) API 호출 실패.
    *   **에러 코드:** HTTP 400 Bad Request 또는 커스텀 API 코드: `PAYMENT_ERROR` + PG 제공 상세 오류 코드 (`DECLINED`, `TIMEOUT`).
    *   **트랜잭션 기록 필요 항목:** 결제 시도 트랜잭션(`Payment_Attempt`)을 별도로 로깅하고, 실패 원인 코드를 반드시 저장.

| UI/UX (Designer) 가이드라인 | 메시징 전략 (Copywriting) | 비고 (Kodari의 검증점) |
| :--- | :--- | :--- |
| **톤앤매너:** 시스템 문제에 대한 안도감과 신뢰 구축. 사용자에게 불편함이 전가되지 않도록 처리해야 함. | **핵심 내용:** "결제가 실패했습니다. 결제 정보를 확인해 주시거나, 다른 결제 수단을 시도해주세요." + **액션 유도:** '재시도' 버튼 강조 및 오류 원인(예: 카드 한도 초과)에 대한 간접적 안내 제공 (개인정보 보호 준수). | 재시도는 무한 루프가 될 수 있습니다. 횟수 제한을 걸고, 3회 이상 실패 시에는 상담 채널로 유도하는 로직이 필요합니다. |

### 🟠 Failure Case 3: 필수 데이터 유효성 검증 실패 (Data Validation Error)
*   **발생 위치:** 진단 테스트(Diagnosis Score calculation) 입력 단계 또는 API 전송 과정.
*   **비즈니스 문제:** 사용자가 의도적으로 잘못된 데이터를 입력하거나, 시스템이 처리할 수 없는 형식의 요청을 보냄.
*   **기술적 원인 (Backend):** 백엔드 스키마 검증(Schema Validation) 실패. (예: `diagnosis_type` 필드가 필수인데 누락됨 / KPI 점수가 정의된 범위를 벗어남).
    *   **에러 코드:** HTTP 400 Bad Request / 커스텀 API 코드: `INVALID_INPUT`
    *   **트랜잭션 기록 필요 항목:** 실패한 요청의 Payload(데이터 구조)를 로깅하여 디버깅에 활용.

| UI/UX (Designer) 가이드라인 | 메시징 전략 (Copywriting) | 비고 (Kodari의 검증점) |
| :--- | :--- | :--- |
| **톤앤매너:** 명확하고 친절하게, 어떤 항목을 *어떻게* 고쳐야 하는지 안내. 지적하는 뉘앙스 금지. | **핵심 내용:** "⚠️ [필드명]에 대한 정보가 필요합니다." + **구체적인 가이드:** '예시: 3~5개 항목을 선택해주세요.'와 같이 최소한의 요구사항을 제시해야 합니다. | 가장 흔하지만, 사용자 경험을 해치기 쉬운 부분입니다. 에러 메시지에 *어디*를 고쳐야 하는지 포인터(Focus)가 명확해야 합니다. |

### 🔵 Failure Case 4: 시스템 내부 오류 (Service Unavailability / Downtime)
*   **발생 위치:** Funnel Flow의 어느 지점에서도 발생 가능.
*   **비즈니스 문제:** 서버 과부하, 외부 API(예: AI 엔진) 연결 끊김 등 시스템 자체 문제가 발생함.
*   **기술적 원인 (Backend):** 백엔드 서비스 중단 또는 DB 연결 실패.
    *   **에러 코드:** HTTP 503 Service Unavailable / 커스텀 API 코드: `SYSTEM_UNAVAILABLE`
    *   **트랜잭션 기록 필요 항목:** 장애 발생 시각, 영향을 받는 모듈(`module=AI_ENGINE`), 재시도 로직 실행 여부 등을 상세히 로깅.

| UI/UX (Designer) 가이드라인 | 메시징 전략 (Copywriting) | 비고 (Kodari의 검증점) |
| :--- | :--- | :--- |
| **톤앤매너:** 투명하고 사과하는 태도. 시스템이 불안정하지 않다는 신뢰를 잃지 않도록 관리해야 함. | **핵심 내용:** "현재 [서비스]에 일시적인 문제가 발생했습니다. 잠시 후 다시 시도해 주세요." + **대안 제시:** '이런 상황에서는 이 자료를 먼저 확인해주세요.' 등 다른 대체 경로(Alternative Path)를 제공하여 사용자가 앱을 닫지 않도록 유도. | 가장 어려운 경우입니다. 사용자에게 시스템의 *불완전함*을 느끼게 해서는 안 됩니다. 백그라운드에서 재시도 로직이 돌아가고 있음을 간접적으로 알려주는 것이 좋습니다. |
