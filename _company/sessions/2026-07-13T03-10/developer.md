## ⚙️ 1. 아키텍처 개요: 데이터 흐름 (Data Flow & Logic Check)

Module C 영상의 핵심은 '진단 테스트 → 점수 계산 → 시각화'라는 단일 비동기 로직입니다. 이 과정에서 발생 가능한 모든 병목 지점과 예외 처리가 기술 문서에 포함되어야 합니다.

**[기술 흐름도 (Simplified Flow)]**
1.  **(User Input)**: 사용자 진단 데이터 입력 (영상 속 가상 테스트 결과). $\rightarrow$ **API Call: `/api/v1/diagnosis_score`**
2.  **(Backend Processing)**: 백엔드 서버가 데이터를 수신하고, `DiagnosisResult` 스키마에 맞춰 KPI(`Growth`, `Engagement`, `Monetization`)를 계산합니다. (데이터 유효성 검증 필수) [근거: sessions/2026-05-18T14-34/developer.md]
3.  **(API Response)**: 진단 점수와 세부 KPI 데이터를 클라이언트(프론트엔드 시각화 레이어)에 전달합니다.
4.  **(Client Display)**: 프론트엔드가 받은 데이터로 UI를 렌더링합니다.

## 💻 2. API 연동 스펙 및 구현 상세 (API Specification & Implementation Details)

### A. 핵심 엔드포인트: Diagnosis Score Calculation
*   **Endpoint:** `GET /api/v1/diagnosis_score`
*   **Request Body (Input):** 진단 테스트를 통해 얻은 원본 데이터가 JSON 형태로 전송됩니다.
    ```json
    {
      "context_id": "uuid-string", 
      "diagnosis_type": "vocal_growth", // 필수: 진단 유형 명시 (RBAC 체크 대상)
      "raw_data": [/* Array of raw scores/metrics */] 
    }
    ```
*   **Response Body (Success):** 계산된 최종 점수와 세부 지표가 반환됩니다.
    ```json
    {
      "success": true,
      "diagnosis_score": { // 핵심 지표
        "overall_score": 78,  // 전체 진단 점수 (0~100)
        "growth_kpi": 85,    // 성장 잠재력 (Growth)
        "engagement_kpi": 62,// 몰입도/활용도 (Engagement)
        "monetization_kpi": 78 // 수익화 가능성 (Monetization)
      },
      "context_id": "uuid-string",
      "status_message": "Data analysis completed successfully."
    }
    ```

### B. 데이터 검증 및 권한 체크 로직 (Critical Logic Integration)
1.  **RBAC 필수 적용:** API는 호출하는 사용자의 `diagnosis_type`에 대한 접근 권한을 반드시 확인해야 합니다. 만약 무료 사용자(`role: free`)가 유료 분석 영역인 'Monetization' 점수를 요청하면, 즉시 403 Forbidden 에러를 반환하고 시각화 레이어에 "Premium Feature" 메시지를 출력해야 합니다. [근거: sessions/2026-05-18T13-43/developer.md]
2.  **KPI 유효성 검증:** `Growth`, `Engagement`, `Monetization` 값은 반드시 0~100 범위 내의 정수형(Integer)으로 제한되어야 합니다. 범위를 벗어나는 값이 들어오면 백엔드에서 강제로 클리핑(`Math.min/max`)하거나, 에러를 발생시켜 시스템 오류 처리를 유도해야 합니다.

## 💥 3. 필수 안정성 확보: Fallback Plan (System Resilience)

영상 제작 시 가장 중요한 것은 '실패했을 때의 대응'입니다. 다음 세 가지 상황에 대한 **시각적 처리 방법**을 명확히 정의합니다.

| 발생 상황 | 기술적 원인 | 사용자에게 보여줄 메시지/처리 방식 | 디자인 시스템 적용 |
| :--- | :--- | :--- | :--- |
| **A. API Time-Out (가장 흔함)** | 서버 부하, 네트워크 지연 등 (3초 초과) | "잠시만 기다려 주세요. 데이터 분석 중입니다." (로딩 상태 유지) | `Loading State`를 최대 5초까지 유지하며, 애니메이션으로 사용자 이탈 방지. |
| **B. Data Error (KPI 유효성 문제)** | 입력된 raw_data가 스키마와 맞지 않거나 KPI 값이 범위를 벗어남. | "데이터 분석에 오류가 발생했습니다. 다시 시도해 주세요." | `Error State`를 사용하며, Primary Color 배경 위에 Accent Color로 경고 표시 (`#FFD700`). |
| **C. RBAC Error (권한 문제)** | 사용자 권한 부족으로 특정 KPI 접근 불가. | "이 기능은 Premium Plan에서만 이용 가능합니다." | `Access Denied State`를 사용하며, Primary Color 배경 위에 ⛔️ 아이콘과 함께 표시. |

## ✨ 4. 디자인 시스템 통합 규칙 (Design System Integration)

기술적인 요소(로딩, 에러, 성공)에도 확정된 디자인 시스템을 적용해야 합니다.

*   **Primary Color (#0A2463):**
    *   사용자 인터페이스의 기본 배경색 및 CTA 버튼에 사용됩니다.
    *   **[기술적 활용]**: 로딩 스피너나 핵심 컴포넌트의 경계선 등 '기본 상태'를 표현하는 데 사용합니다.
*   **Accent Color (#FFD700):**
    *   경고, 주의, 또는 주요 액션(CTA)에만 제한적으로 사용됩니다. **오류 메시지나 데이터 임계값 초과 구간**을 시각화할 때 필수적입니다.
    *   **[기술적 활용]**: Fallback Plan B (Data Error) 발생 시 텍스트 하이라이팅 및 경고 아이콘 색상으로 강제 지정합니다.
