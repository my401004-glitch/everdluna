### 🧪 Gap Score 시스템 데이터 연동 시나리오 검증 (3가지 유형)

제시된 스크립트와 데이터 요구사항을 기반으로, 가장 취약하거나 중요한 세 가지 핵심 테스트 케이스를 정의했습니다. 이들은 기존에 설계했던 `Growth`, `Engagement`, `Monetization` KPI 로직과 결합하여 시스템의 안정성을 최대화하는 데 중점을 둡니다.

#### 1. [유형 A] Boundary & Edge Case: 데이터 유효성 및 범위 검증 (Data Integrity Test)
*   **왜 필요한가?**: 외부 API나 사용자 입력은 항상 예측 불가능한 데이터를 가져옵니다. 예를 들어, `Gap Score` 값이 음수이거나(논리적으로 불가), 혹은 너무 큰 값(`Infinity`)으로 들어올 수 있습니다. 또한, 필수 KPI 필드 중 하나라도 누락될 경우 시스템 전체가 깨집니다. [근거: sessions/2026-05-18T14-34/developer.md]
*   **테스트 목표**: 백엔드 진단 컨트롤러 (`diagnosisController`) 레벨에서 데이터 유효성을 강하게 검증하고, 에러 발생 시 사용자에게 명확한 피드백을 제공해야 합니다.
*   **시나리오 (Test Case)**:
    1.  **KPI 누락 테스트**: `result_data` JSON 스키마에 정의된 3개 KPI 중 하나(예: `Growth`)가 아예 없는 데이터로 요청했을 때, API는 **400 Bad Request**를 반환하고 "필수 KPI 필드 'Growth'가 누락되었습니다."라는 상세 에러 메시지를 돌려주어야 합니다.
    2.  **범위 초과 테스트**: Gap Score 값이 허용 범위를 벗어났을 때 (예: -10점 또는 150점), 시스템은 해당 값을 클리핑(Clamping)하여 로직에 투입하거나, 최대/최소 경고를 발생시켜야 합니다.
    3.  **비정형 데이터 테스트**: `context_id`가 UUID 형식이 아닌 문자열이나 숫자로 들어왔을 때, DB 삽입 전에 타입 캐스팅 및 강제 변환 로직이 동작하는지 검증합니다.

#### 2. [유형 B] Authorization & Role-Based Access Control (RBAC) 테스트
*   **왜 필요한가?**: Gap Score는 매우 민감한 '성장 서사' 데이터입니다. 모든 사용자에게 동일하게 노출되어서는 안 됩니다. 무료 사용자(Trial User)에게 유료 기능인 깊이 있는 진단 결과(`Depth` 지표 등)를 제공할 경우 비즈니스 로직이 붕괴합니다. [근거: sessions/2026-05-18T13-43/developer.md]
*   **테스트 목표**: 사용자의 현재 '권한(Role)'과 요청하는 데이터의 '민감도'를 비교하여 접근 가능 여부를 사전에 차단해야 합니다.
*   **시나리오 (Test Case)**:
    1.  **권한 미달 테스트**: `is_paid` 플래그가 `false`인 사용자(무료 체험자)가 특정 `diagnosis_type` (예: 'Deep-Dive Analysis')를 요청했을 때, API는 **403 Forbidden**을 반환하고 "이 기능은 프리미엄 구독이 필요합니다."라는 명확한 메시지를 제공해야 합니다.
    2.  **권한 초과 테스트**: 관리자(Admin) 권한 사용자가 특정 데이터 필드(`Monetization`)의 접근이 제한되어 있음에도 불구하고, API가 해당 값을 반환하려 할 때, 백엔드가 강제로 `null` 또는 마스킹 처리된 값으로 대체하는지 검증합니다.

#### 3. [유형 C] Workflow & State Transition Test (시스템 순서 검증)
*   **왜 필요한가?**: Gap Score는 일회성 이벤트가 아니라, '진단(Diagnosis)' $\rightarrow$ '개선 계획 수립(Action Plan)' $\rightarrow$ '재측정(Re-diagnosis)'의 사이클로 반복됩니다. 이전 세션의 결과가 다음 진단에 영향을 주지 않거나, 혹은 적절히 반영되어야 합니다. [근거: sessions/2026-05-18T16-34/developer.md]
*   **테스트 목표**: 시간의 흐름과 사용자 액션에 따른 시스템 상태 변화가 논리적으로 매끄러운지 검증합니다.
*   **시나리오 (Test Case)**:
    1.  **시간 경과 무효화 테스트**: A라는 진단(Day 1)을 받은 후, 사용자가 아무런 행동 없이 30일이 지난 시점(Day 31)에 B라는 진단을 요청했을 때, 시스템은 Day 1의 데이터가 만료되었음을 인지하고, `Diagnosis_Results` 테이블에 **새로운 Context ID**를 부여하며 이전 데이터를 참고용으로만 제시해야 합니다.
    2.  **행동 기반 변화 감지 테스트**: 사용자가 '추천 행동' (예: 특정 연습 영상 시청)을 완료한 직후 재진단 요청 시, 시스템이 단순 Gap Score 변화 외에 **'실제 개선 노력 지수(Effort Index)'**를 추가하여 점수에 반영하는지 검증해야 합니다.
